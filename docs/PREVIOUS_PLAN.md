# LOSTORY Product Requirements

문서 상태: Draft  

최종 갱신일: 2026-07-03  

문서 목적: 팀 내부 합의와 HWP 제출 문서 작성의 기준  

관련 산출물: `소프트웨어공모전_기획안_구글독스.pdf`, `행복한 감자들_1차서류보고서_AI소프트웨어공모전.hwp`

## 1. 한 줄 정의

LOSTORY는 생활권 단위에 흩어진 분실물 정보를 구조화하고, 분실 신고와 습득물 정보를 비교해 가능성이 높은 후보를 제공하는 로컬 분실물 매칭 서비스다.

## 2. 핵심 포지션

LOSTORY는 LOST112 같은 공식 유실물 체계를 대체하지 않는다. 공식 절차로 이어지기 전 로컬 단계에서 흩어진 습득물 정보와 분실 신고를 정리하고, 분실자가 확인할 만한 후보를 빠르게 좁혀 보관처 또는 관리 담당자 확인 절차로 연결하는 서비스다.

이 서비스는 최종 소유자를 자동으로 판정하지 않는다. 최종 소유자 확인과 실제 반환 판단은 분실물 관리 담당자가 보관 절차에 따라 진행한다.

## 3. 문제 정의

분실물 문제는 물건이 단순히 사라져서 생기는 문제가 아니라, 습득물 정보가 여러 로컬 채널에 흩어져 분실자와 제때 연결되지 못하는 정보 연결 실패에 가깝다.

분실물 정보는 공식 유실물 체계뿐 아니라 지역 커뮤니티, 학교 게시판, 주변 상점, 행사 운영본부, 임시 보관처 등 다양한 채널에 올라온다. 분실자는 여러 채널을 반복 확인해야 하며, 습득자는 물건을 어디에 맡겨야 할지 몰라 공식 절차까지 이어가지 못하는 경우가 생긴다.

정보를 한곳에 모으면 반환 가능성은 높아지지만, 후보 사진과 상세 정보가 무분별하게 공개될 경우 허위 소유 주장 위험도 커진다. 따라서 LOSTORY는 모든 분실물 정보를 공개하는 검색 서비스가 아니라, 상세 분실 신고를 기반으로 후보를 제한 제공하는 매칭 서비스로 설계한다.

## 4. 목표

| 목표 | 설명 |

|---|---|

| 로컬 정보 구조화 | 생활권 단위에 흩어진 습득물 정보와 분실 신고를 하나의 데이터 구조로 관리한다. |

| 후보 매칭 | 사진, 위치, 시간, 카테고리, 색상, 텍스트 정보를 비교해 관련성이 높은 후보를 제공한다. |

| 탐색 비용 절감 | 분실자가 여러 게시판, 커뮤니티, 안내소를 반복 확인하는 부담을 줄인다. |

| 악용 위험 완화 | 전체 목록 공개 대신 후보 제한 제공과 로그 기반 위험 관리를 적용한다. |

| 관리 흐름 분리 | 서비스는 후보를 좁히고, 최종 확인과 반환은 분실물 관리 담당자가 수행한다. |

## 5. 비목표

| 제외 범위 | 이유 |

|---|---|

| LOST112 직접 연동 | 외부 공식 시스템 연동은 정책, 권한, 일정 리스크가 크다. MVP에서는 안내 수준으로 둔다. |

| 서비스 내 소유권 자동 판정 | 시스템 점수만으로 실제 소유자를 확정하면 법적, 운영적 책임이 커진다. |

| 습득자 로그인 필수화 | 습득물 등록 장벽이 높아져 데이터 수집 가능성이 낮아진다. |

| 자체 AI 모델 학습 | 데이터와 시간이 부족하고 GPU 운영 부담이 크다. MVP에서는 외부 AI/Vision API를 활용한다. |

| 시 단위 전체 서비스 | 초기 구현 범위가 과도하다. MVP는 행사 및 학교 근처에서 검증한다. |

| 서비스 관리자 | 서비스 전체 정책, 계정 승인, 악용 사용자 관리를 담당하는 내부 운영자 | 필요 |

### 6.1 분실물 관리 계정 유형

| 유형 | 설명 | 예시 |

|---|---|---|

| 분실물센터 계정 | 장기적으로 분실물을 보관하고 관리하는 계정 | 학교 분실물센터, 도서관, 기관 안내데스크, 시설 관리팀 |

## 7. 주요 사용자 흐름

### 7.1 습득물 등록

1. 습득자가 로그인 없이 등록 화면에 접근한다.

2. 사진, 발견 위치, 발견 시간, 물품 카테고리, 간단한 설명을 입력한다.

3. 물건을 기관에 인도한 경우 인도한 보관처를 선택한다.

4. 시스템은 습득물 데이터를 저장하고, 사진에서 특징 후보를 추출하거나 수동 입력값을 저장한다.

5. 등록된 습득물은 해당 행사 또는 분실물센터 관리 화면에 표시된다.

### 7.2 분실 신고 및 후보 확인

1. 분실자가 회원가입 및 로그인한다.

2. 물품 종류, 추정 위치, 날짜 및 시간, 색상, 설명, 필요 시 사진을 입력한다.

3. 시스템은 분실 신고와 습득물 데이터를 비교해 `match_score`를 계산한다.

4. 매칭 점수가 높은 후보 Top N을 제한적으로 제공한다.

5. 분실자는 후보의 보관처 또는 관리 담당자 안내를 확인한다.

6. 실제 소유자 확인과 반환은 분실물 관리 담당자가 보관 절차에 따라 처리한다.

### 7.3 분실물 관리

1. 분실물 관리 주체가 행사 계정 또는 분실물센터 계정을 생성한다.

2. 관리 담당자는 접수된 습득물을 조회한다.

3. 보관 위치, 상태, 반환 여부를 관리한다.

4. 상태는 최소 `보관중`, `확인중`, `반환완료`를 사용한다.

5. 반환이 끝난 물건은 반환완료 상태로 기록한다.

## 8. MVP 기능 요구사항

| ID | 기능 | 우선순위 | 요구사항 | 완료 기준 |

|---|---|---|---|---|

| MVP-01 | 습득물 등록 | P0 | 습득자가 로그인 없이 사진, 발견 위치, 발견 시간, 설명을 등록한다. | 습득물 1건이 DB에 저장되고 관리 화면에 표시된다. |

| MVP-02 | 분실 신고 등록 | P0 | 분실자가 로그인 후 상세 분실 정보를 등록한다. | 분실 신고 1건이 저장되고 후보 매칭을 요청할 수 있다. |

| MVP-03 | 이미지 특징 추출 | P0 | 외부 AI/Vision API 또는 더미 결과로 카테고리, 색상, 특징 후보를 저장한다. | 사진 입력 시 매칭에 사용할 구조화된 특징값이 저장된다. |

| MVP-04 | 후보 매칭 | P0 | 위치, 시간, 카테고리, 색상, 텍스트 유사도로 `match_score`를 계산한다. | 후보 Top N이 점수순으로 반환된다. |

| MVP-05 | 후보 제한 제공 | P0 | 전체 목록 대신 매칭 후보만 제한적으로 보여준다. | 분실자가 후보 목록과 보관처 안내를 확인할 수 있다. |

| MVP-06 | 분실물 관리 계정 | P0 | 행사 계정과 분실물센터 계정을 구분해 상태를 관리한다. | 보관중, 확인중, 반환완료 상태 변경이 가능하다. |

| MVP-07 | 악용 위험 관리 | P0 | 검색, 후보 조회, 후보 클릭 로그를 저장하고 위험 신호를 계산한다. | 반복 검색, 후보 과다 열람 등 의심 패턴을 확인할 수 있다. |

| MVP-08 | 공식 절차 안내 | P1 | LOST112 등 공식 유실물 체계 안내 문구를 제공한다. | 후보가 없거나 공식 신고가 필요한 경우 안내 문구를 확인할 수 있다. |

## 9. 매칭 방식

MVP에서는 학습 기반 랭킹 모델이 아니라 설명 가능한 단순 가중합으로 시작한다.

```text

match_score =

  0.25 * location_score

+ 0.20 * time_score

+ 0.20 * category_score

+ 0.15 * color_score

+ 0.20 * text_similarity_score

```

위 가중치는 MVP 초안이다. 실제 구현 전 팀 논의로 조정할 수 있다.

| 점수 | 의미 |

|---|---|

| location_score | 분실 추정 위치와 발견 위치가 가까운 정도 |

| time_score | 분실 추정 시간과 발견 시간이 가까운 정도 |

| category_score | 물품 카테고리가 일치하는 정도 |

| color_score | 색상 정보가 유사한 정도 |

| text_similarity_score | 분실자가 입력한 설명과 습득물 설명 또는 AI 설명이 유사한 정도 |

## 10. 후보 제한 제공 정책

LOSTORY는 전체 분실물 목록을 공개적으로 보여주지 않는다. 분실자가 입력한 상세 정보와 관련성이 높은 후보만 제한적으로 제공한다.

제공 가능한 정보:

- 물품 카테고리

- 대략적인 색상

- 발견 위치 범위

- 발견 시간 범위

- 보관처 또는 관리 담당자 안내

- 일부 처리된 썸네일

제한하거나 관리 절차로 넘길 정보:

- 고해상도 원본 사진

- 세부 식별 특징

- 민감한 내용물 정보

- 담당자 직접 연락처

## 11. 악용 위험 관리

분실물 정보가 한곳에 모이면 허위 소유 주장, 후보 탐색, 고가 물품 노림수 같은 위험이 생긴다. MVP에서는 규칙 기반 `abuse_score`로 시작한다.

예시 신호:

- 짧은 시간 동안 반복 검색

- 고가 물품 키워드 반복 검색

- 후보 상세 과다 조회

- 위치 조건을 바꿔가며 넓게 탐색

- 여러 분실 신고를 빠르게 생성

대응:

- 후보 노출 축소

- 관리자 검토 대상 표시

- 일정 시간 검색 제한

- 보관처 직접 확인 안내

## 12. 기술 구성

| 영역 | 선택 | 이유 |

|---|---|---|

| Frontend | React Native | iOS와 Android에서 동일한 사용자 흐름을 제공한다. |

| Backend | Spring Boot REST API | 인증, 권한, 도메인 상태, 매칭, 로그를 일관되게 관리한다. |

| DBMS | PostgreSQL + PostGIS | 관계형 데이터와 위치 좌표 기반 검색을 함께 처리한다. |

| Storage | Object Storage 또는 S3 호환 저장소 | 사진 원본과 썸네일을 DB와 분리해 저장한다. |

| CV/AI | Google Cloud Vision API 또는 외부 AI/Vision API | MVP에서 자체 모델 학습 없이 사진 특징을 추출한다. |

| Cache | Redis 선택 | 반복 검색 카운터, rate limit, 후보 캐시에 사용한다. |

| Queue | MQ 선택 | 이미지 특징 추출이나 알림을 비동기화할 때 도입한다. |

| AI Service | Python 선택 | OpenCV, PyTorch, 로컬 모델 추론이 확정될 때만 분리한다. |

AI/Vision API는 판단 주체가 아니다. 사진에서 카테고리, 색상, 브랜드 후보, 짧은 설명문 같은 특징을 추출하는 보조 역할만 수행한다. 후보 매칭, 상태 관리, 로그 저장, 후보 노출 정책은 Spring Boot 서버가 담당한다.
