## 1. 개요

### 한 줄 요약

축제 및 학교 근처에서 발생한 습득물 사진과 분실자의 신고 내용을 AI로 매칭하고, 비공개 특징 검증과 악용 탐지를 통해 안전한 반환을 돕는 분실물 매칭 서비스.

### 이 문서를 읽어야 하는 이유

이 문서는 심사위원 제출용 최종 기획서가 아니라, 팀원 3명이 같은 기준으로 기획서, 구조도, UI, 기능 범위를 작성하기 위한 내부 기준 문서다.  

각 팀원은 이 문서를 기준으로 다음을 판단한다.

- 우리가 무엇을 만들고, 무엇은 만들지 않는지

- MVP 범위가 어디까지인지

- 각 기능이 완료되었다고 판단하는 기준이 무엇인지

- 교수님 심사에서 기술성과 구현 가능성을 어떻게 보여줄지

- 공적 기획서에 어떤 구조도와 UI 흐름을 넣어야 하는지

## 3. 배경 및 문제 정의

### 3.1 공식 유실물 시스템이 이미 존재한다

이 사실은 두 가지를 의미한다.

1. 분실물 문제는 공공성이 있는 실제 문제다.

2. 이미 공식 체계가 있으므로, 우리 서비스는 이를 대체한다고 주장하면 안 된다.

따라서 우리 서비스의 포지션은 다음과 같이 잡는다.

&gt; 학교/행사장/기관 단위에서 분실물 정보를 빠르게 구조화하고, 분실자와 습득물을 더 높은 확률로 연결한 뒤, 필요한 경우 공식 보관처로 안내하는 보조 매칭 플랫폼.

### 3.2 기존 방식의 한계

기존 분실물 처리 방식의 핵심 한계는 "정보가 없어서 못 찾는 것"보다 "정보가 흩어져 있고 서로 매칭되지 않는 것"에 가깝다.

분실자 관점:

- 정확한 분실 시간과 장소를 기억하지 못한다.

- "검은색 지갑", "에어팟", "카드지갑"처럼 비슷한 물건이 많다.

- 여러 게시판, 안내소, 공식 포털을 직접 찾아야 한다.

- 습득물이 나중에 등록되면 다시 검색하지 않는 이상 놓칠 수 있다.

습득자 관점:

- 어디에 신고해야 하는지 모를 수 있다.

- 직접 기관에 가져가는 과정이 번거롭다.

- 물건을 발견했지만 설명을 자세히 적기 어렵다.

- 사진만 찍어두고 나중에 처리하려는 경우가 많다.

행사/센터 관리자 관점:

- 사진 등록, 물품명 작성, 특징 기록, 문의 응대, 반환 상태 관리가 반복 작업이다.

- 비슷한 물건이 많으면 소유자 확인이 어렵다.

- 고가 물품은 허위 소유 주장에 취약하다.

- 반환 완료, 보관중, 확인중 같은 상태가 체계적으로 관리되지 않으면 운영 혼선이 생긴다.

### 3.3 축제 및 학교 근처를 1차 타깃으로 잡는 이유

시 단위 서비스는 장기적으로 의미가 있지만, 공모전 MVP로는 범위가 넓고 외부기관 연동이 필요해 구현 리스크가 크다. 반면 축제 및 학교 근처는 다음 장점이 있다.

- 공간 범위가 비교적 명확하다.

- 행사 기간이 정해져 있어 데이터 수집과 시연이 쉽다.

- 분실물센터 또는 행사 운영본부가 존재한다.

- 학생, 방문객, 운영진이라는 사용자 역할이 명확하다.

- 데모용 더미 데이터를 구성하기 쉽다.

- 교수님 심사에서 구현 가능성을 설명하기 좋다.

결론:

&gt; 2026-07-03 제출 기획서에서는 "축제 및 학교 근처"를 MVP로 고정하고, "시 단위 확장"은 장기 비전으로만 배치한다.

## 6. 차별성/경쟁력

### 6.1 단순 검색이 아니라 매칭 문제로 정의한다

기존 접근은 사용자가 직접 키워드, 장소, 시간을 입력해 검색하는 방식이다.  

우리 서비스는 습득물과 분실 신고를 각각 구조화한 뒤, 두 데이터를 비교해 후보를 자동 랭킹한다.

핵심 차이:

- 기존: 사용자가 직접 검색

- 본 서비스: 시스템이 후보를 자동 추천

### 6.2 행사와 분실물센터를 모두 지원한다

행사는 단발성이고, 분실물센터는 장기 운영이다. 두 유형을 분리하면 실제 운영 환경을 더 설득력 있게 설명할 수 있다.

- 행사 계정: 축제 기간 중 빠른 등록과 반환에 집중

- 분실물센터 계정: 장기 보관, 상태 관리, 문의 응대에 집중

### 6.3 비공개 특징 검증을 핵심 보안 구조로 둔다

분실물 서비스는 물건을 찾아주는 편의성만으로는 부족하다. 고가 물품은 허위 소유 주장 위험이 있다.  

따라서 후보 상세정보를 먼저 보여주지 않고, 사용자가 본인만 알 수 있는 정보를 먼저 입력하게 한다.

예시:

- 지갑 안에 있던 카드 종류

- 케이스나 물건의 흠집 위치

- 각인 또는 스티커 위치

- 전자기기 잠금화면 특징

- 일련번호 일부

이 구조는 다음 메시지로 설명할 수 있다.

&gt; 사진을 보고 맞히는 서비스가 아니라, 소유자만 아는 정보를 먼저 증명해야 상세정보를 볼 수 있는 서비스.

### 6.4 악용 탐지를 P0에 포함한다

많은 팀이 분실물 매칭에서 "찾아준다"만 강조할 수 있다.  

우리 팀은 "잘못 가져가는 것을 막는다"까지 P0에 포함한다.

P0 악용 탐지 대상:

- 짧은 시간 내 반복 검색

- 같은 위치에서 브랜드/색상/카테고리만 바꿔 검색

- 후보 열람 과다

- 소유권 검증 실패 누적

- 고가 키워드 반복

공모전 기획서에서는 이 지점을 기술적 차별성으로 강조한다.

### 6.5 공식 유실물 체계를 대체하지 않는다

LOST112와 같은 공식 체계는 이미 존재한다.  

본 서비스는 이를 대체하지 않고, 학교/행사장/기관 단위에서 1차 매칭과 운영 관리를 돕는 보조 플랫폼으로 포지셔닝한다.  

공식 보관처가 필요한 경우 위치, 연락처, 운영시간 안내 수준으로 연결한다.

## 7. 기술 스택 및 구현 방안

### 7.1 권장 기술 방향

현재 팀 구성은 프론트엔드 1명, 백엔드 1명, 백엔드&amp;팀장 1명이다.  

교수님 심사에서 기술성과 구현 가능성을 동시에 보여주려면, 과도한 AI 모델 학습보다 "명확한 시스템 구조 + 구현 가능한 AI/API 활용 + 점수화 로직"이 더 적합하다.

백엔드는 Spring Boot를 기본 축으로 둔다. 인증/권한, 기업회원, 행사/센터, 습득물/분실 신고, 후보 랭킹, 상태 관리, 로그 저장, REST API는 Java/Spring에서 처리하는 것을 기본 전제로 한다.

Python은 기본 백엔드가 아니라, 이미지 처리 또는 가벼운 로컬 모델이 실제로 필요해질 때만 보조 마이크로서비스로 분리한다. 예를 들어 OpenCV 전처리, PyTorch/Transformers 기반 임베딩 추출, 로컬 VLM/SLM 추론이 붙는 경우에만 Python 서비스를 둔다.

기본 원칙:

- P0는 Spring Boot 중심으로 구현한다.

- Python 서비스는 "필요해지면 붙이는 선택지"로 둔다.

- DB의 원천 데이터는 Spring Boot가 관리한다.

- Python 서비스는 가능하면 stateless하게 두고, 이미지 또는 텍스트를 받아 특징 결과만 반환한다.

- MQ, Redis, REST API, 로그 처리 등은 우선 Java/Spring 생태계에서 해결한다.

- 마이크로서비스 분리는 기술 과시용이 아니라, Java에서 처리하기 어려운 AI/이미지 처리 책임이 생겼을 때만 적용한다.

### 7.4.1 Spring 중심 아키텍처 권장안

P0 기준 권장 구조:

```text

React/Next.js Frontend

  -&gt; Spring Boot REST API

      -&gt; Auth/Authorization

      -&gt; Organization/Event/Center

      -&gt; FoundItem/LostReport

      -&gt; Match Scoring

      -&gt; Claim Verification

      -&gt; Abuse Detection

      -&gt; Search Log

      -&gt; DB

      -&gt; File Storage

      -&gt; External AI API

```

이미지 처리나 로컬 모델이 추가될 때의 확장 구조:

```text

React/Next.js Frontend

  -&gt; Spring Boot REST API

      -&gt; DB/File Storage

      -&gt; MQ or Internal REST

          -&gt; Python Image/Model Service

              -&gt; feature extraction result

      -&gt; Spring stores extracted features

```

이 구조에서 Spring Boot는 시스템의 중심이다. Python 서비스는 "이미지/모델 계산기" 역할만 수행하고, 사용자 권한, 상태 변경, 매칭 후보 저장, 검증 이력, 악용 로그는 Spring이 관리한다.

MQ를 도입할 경우의 명확한 사용처:

- 이미지 특징 추출을 비동기로 처리한다.

- API 응답을 빠르게 반환하고, 추출 완료 후 상태를 갱신한다.

- 추후 알림 기능이 붙을 때 이벤트 기반으로 확장한다.

Redis를 도입할 경우의 명확한 사용처:

- 같은 분실 신고에 대한 후보 Top 5 결과를 짧게 캐싱한다.

- 짧은 시간 내 반복 검색 횟수를 카운트한다.

- 로그인/인증 rate limit 또는 악용 탐지 카운터에 사용한다.

P0에서 MQ/Redis를 반드시 구현할 필요는 없다. 다만 공적 기획서에는 "확장 가능한 구조"로 언급할 수 있다.

### 7.6 매칭 점수 MVP 초안

MVP에서는 학습 기반 모델이 아니라 단순 가중합으로 시작한다.  

이는 구현 가능성을 높이고, 교수님에게 로직을 설명하기 쉽다.

임시 산식:

```text

match_score =

  0.25 * location_score

+ 0.20 * time_score

+ 0.20 * category_score

+ 0.15 * color_score

+ 0.20 * text_similarity_score

```

[수정 필요: 가중치와 각 score 계산 방식]

각 점수의 의미:

| 점수 | 의미 | 예시 |

|---|---|---|

| location_score | 분실 위치와 발견 위치가 가까운 정도 | 같은 행사장 구역이면 높음 |

| time_score | 분실 추정 시간과 발견 시간이 가까운 정도 | 30분 이내면 높음 |

| category_score | 물품 카테고리가 일치하는 정도 | 지갑/카드지갑/가방 등 |

| color_score | 색상 정보가 유사한 정도 | 검정/짙은 회색 등 |

| text_similarity_score | 사용자 설명과 AI 설명/공개 설명이 유사한 정도 | "검은 카드지갑" vs "검정색 카드 케이스" |

비공개 특징은 후보 랭킹보다 소유권 검증 단계에서 사용하는 것을 기본으로 한다.

### 7.7 악용 위험 점수 MVP 초안

악용 탐지는 P0에 포함한다. 다만 구체 산식은 아직 확정 전이다.

임시 산식:

```text

abuse_score =

  0.20 * repeated_query_score

+ 0.20 * high_value_keyword_score

+ 0.20 * failed_claim_score

+ 0.15 * candidate_probing_score

+ 0.15 * location_fishing_score

+ 0.10 * multi_account_similarity_score

```

[수정 필요: abuse_score 산식, feature 정의, 임계값]

임시 대응 기준:

| abuse_score | 처리 |

|---:|---|

| 0-30 | 정상 |

| 30-60 | 후보 상세정보 제한 |

| 60-80 | 추가 인증 또는 비공개 특징 선입력 요구 강화 |

| 80-100 | 관리자 검토, 임시 제한, 기관 확인 필요 |

P0 완료 기준:

- 검색 로그가 저장된다.

- 검증 실패 횟수가 저장된다.

- abuse_score가 계산된다.

- abuse_score에 따라 후보 상세정보 공개 여부가 달라진다.

## 14. 공적 기획서 작성 시 강조 문장

아래 문장은 제출용 기획서에 다듬어 넣을 수 있다.

### 14.1 문제 정의 문장

분실물 문제는 물건이 존재하지 않아서 발생하는 문제가 아니라, 분실자와 습득물 정보가 서로 연결되지 않아 발생하는 문제다. 특히 축제나 학교 근처처럼 짧은 시간에 많은 사람이 오가는 환경에서는 비슷한 물건이 다수 발생하고, 운영자는 수작업으로 등록과 반환을 관리해야 하며, 분실자는 여러 경로를 직접 검색해야 한다.

### 14.2 해결 방향 문장

본 서비스는 습득물 사진과 분실 신고 정보를 구조화하고, 위치·시간·카테고리·색상·텍스트 유사도를 기반으로 후보를 자동 랭킹한다. 또한 후보 상세정보를 바로 공개하지 않고, 소유자만 알 수 있는 비공개 특징을 먼저 검증함으로써 허위 소유 주장 위험을 줄인다.

### 14.3 기술성 강조 문장

본 시스템은 단순 게시판형 분실물 관리가 아니라, 이미지 특징 추출, 복합 점수 기반 후보 랭킹, 비공개 특징 기반 소유권 검증, 로그 기반 악용 위험 점수화를 결합한 매칭 시스템이다. 초기 MVP에서는 규칙 기반 가중합으로 구현 가능성을 확보하고, 향후 정답 매칭 데이터가 축적되면 학습 기반 랭킹 모델로 확장할 수 있다.

### 14.4 구현 가능성 강조 문장

MVP는 시 단위 전체 서비스를 목표로 하지 않고, 학교 축제 및 학교 근처라는 제한된 공간에서 시작한다. 이를 통해 외부기관 연동 없이도 실제 사용 흐름을 검증할 수 있으며, 행사 계정과 분실물센터 계정을 분리해 단발성 운영과 장기 운영을 모두 설명할 수 있다.

### 14.5 차별성 강조 문장

본 서비스의 차별점은 "찾아주는 것"뿐 아니라 "잘못 가져가는 것을 막는 것"까지 포함한다는 점이다. 공개 속성과 비공개 속성을 분리하고, 상세정보 공개 전에 소유자만 알 수 있는 정보를 검증하는 challenge-response 구조를 적용해 분실물 반환의 신뢰성을 높인다.
