# LOSTORY MVP 구현 기준

**상태:** 팀 합의 완료 · 구현 기준 문서
**확정일:** 2026-08-23
**우선순위:** 이 문서의 P0/P1 경계가 이전 제품 기획·API 초안과 다르면 이 문서를 따른다. 기술 작업 순서는 [IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md)를 따른다.

## 1. 서비스와 책임 경계

LOSTORY는 습득자가 가까운 분실물 센터를 선택해 물건을 인계하도록 돕고, 신고자의 장소 핀과 등록된 습득물을 비교해 Top-5 후보를 제시한다. LOST112 같은 공식 체계를 대체하지 않으며, 실제 소유권 판정은 하지 않는다.

| 영역 | LOSTORY의 책임 | 하지 않는 일 |
|---|---|---|
| 센터 안내 | 등록된 활성 센터의 이름·위치·연락처를 거리순으로 안내 | 외부 센터의 실시간 재고·운영 상태 보장 |
| P0 후보 | 모든 `ACTIVE` 습득물에서 점수 기준 Top-5 생성 | 후보만으로 소유권·반환을 확정 |
| P1 후보 상세 | 포인트로 신고 단위 열람 권한을 부여 | 정확한 보관 위치·습득자 신원 공개 |
| 파트너 대시보드 | 센터의 인계 수락·보관·반환과 보상 근거 관리 | P0에서 센터 보관 사실을 자동 검증 |

## 2. 릴리스 경계

### 2.1 P0: 개인 등록, 센터 안내, 점수 후보

- 일반 사용자와 관리자 인증, 개인 습득물 등록, 분실 신고를 제공한다.
- 센터 디렉터리는 인증된 P0 사용자가 조회한다. `center_partnerships`, 센터 담당 권한, 대시보드, 물리 인계 검증은 P0에 없다.
- 후보 풀은 보관 방식과 무관한 모든 `ACTIVE`·미만료 습득물이다.
- P0 후보 배열 `candidates[]`의 각 원소는 `candidateId`, `rank`, `score`만 제공한다. 응답 최상위의 freshness 메타데이터는 허용하며 후보 원소 필드 제한에 포함하지 않는다. 후보 상세 열람·포인트 원장·반환 보상은 P1까지 제공하지 않는다.
- 신고자는 자기 신고를 닫을 수 있지만, 다른 사용자의 습득물을 `RETURNED`로 바꿀 수 없다.

### 2.2 P1: 파트너 센터 대시보드와 포인트

- ADMIN이 오프라인 검토를 마친 **기존 디렉터리 센터**와 새 관리 계정을 연결한다. 기존 일반 계정은 파트너 관리 계정에 연결하지 않는다.
- 등록 시 센터와 관리 계정은 `PENDING`으로 만들고, ADMIN 승인 뒤 24시간·1회 사용 비밀번호 설정 링크를 별도 채널로 전달한다. 재발급은 이전 링크를 즉시 폐기한다.
- 활성 파트너 센터에는 대시보드 전용 관리 계정이 정확히 하나만 있다. 교체는 새 관리 계정을 만들고 이전 계정을 비활성화한다.
- 대시보드는 `USER_CONFIRMED` 대기열을 표시하고, 실물을 확인한 항목만 `CENTER_CONFIRMED`로 수락한다. 거절된 기록은 사용자 진술로 보존한다.
- 담당자만 센터 확인 인계·반환을 기록한다. `RETURNED`, `return_records`, 반환 보상은 이 흐름에서만 만든다.
- P1부터 후보 상세 열람에 포인트를 사용한다. 한 사용자는 하나의 신고에 한 번만 차감되고, 이후 재매칭 후보도 계속 열람할 수 있다.
- 실제 결제 충전·현물 교환·익명 연락 중계·정확한 비센터 보관 위치 공개는 P1 범위가 아니다.

## 3. P0 습득물 등록과 인계 수명주기

### 3.1 등록 순서

1. **사진 업로드:** FE가 BE로 이미지를 업로드한다. 사진 업로드 또는 사진 교체만 새 Vision 작업을 만든다. BE는 소유자만 볼 수 있는 일부 `NULL` 필드의 `DRAFT` 습득물을 만들고 Object Storage에 저장한다.
2. **Vision 추출:** 승인된 단일 외부 Vision 제공사가 이미지에서 특징을 비동기로 추출한다. 일반 서비스 약관에 이미지 처리를 고지한다. 제공사는 학습 미사용, 보존 기간, 처리 지역, 비용 한도를 구현 전에 문서화해야 한다.
3. **장소·시각 입력:** 습득자는 습득 장소와 시각, 물품 분류를 입력한다.
4. **특징 확정:** 습득자는 AI가 제안한 색상·공개 설명을 수정하거나 승인한다. 확정된 공개 특징만 후보 상세에 쓸 수 있고, 원본 AI 결과는 매칭용 내부 기록이다.
5. **보관 방식 결정:** `LEFT_IN_PLACE`, `MOVED_TO_SAFE_PLACE`, `HANDED_TO_CENTER` 중 하나를 선택한다.
6. **인계 확정:** FE/mobile은 NAVER 지도 앱 실행·복귀와 미완료 인계 카드/팝업을 담당한다. BE는 선택된 센터와 `PENDING_HANDOVER`를 제공하고 서버 시각 `handedAt`을 기록한다.

### 3.2 상태와 후보 자격

```text
DRAFT ──등록 필수값·특징·보관 방식 확정──> ACTIVE
  │                                             │
  └─ HANDED_TO_CENTER 선택 ──> PENDING_HANDOVER
                                      │
                          사용자 인계 확정 시 USER_CONFIRMED

ACTIVE ──만료──> EXPIRED
ACTIVE + CENTER_CONFIRMED ──센터 반환 기록──> RETURNED  (P1만)
```

- `DRAFT`는 24시간 뒤 이미지와 함께 자동 정리한다.
- `PENDING_HANDOVER`는 후보에 포함하지 않는다.
- `LEFT_IN_PLACE`와 `MOVED_TO_SAFE_PLACE`는 등록 완료 시 `ACTIVE`가 된다.
- P0 공개 상태는 USER_CONFIRMED이며, 사용자 인계 확인은 센터 검증 전 사용자 진술이다. 여기서 `USER_CONFIRMED`는 API의 `handoverStatus` 값이며, 리소스 `status`는 `ACTIVE`로 유지된다. P1 수락 전까지 소유자가 수정·철회할 수 있다.
- 등록 PATCH는 Vision 작업을 새로 만들지 않고 열린 신고 후보만 stale로 표시한다. 분류·위치·시각·확정 특징 변경은 기존 Vision 결과를 유지하며 매칭 후보를 다시 계산한다.
- Vision이 PENDING 또는 FAILED여도 사용자는 직접 확정한 특징으로 등록을 완료할 수 있다. 누락된 색상·설명 점수는 `0`이다.

### 3.3 센터 선택과 인계 정보

- 습득 장소 기준 서버 정책 반경 1 km 안의 활성 센터를 거리순 최대 10개 반환한다.
- `HANDED_TO_CENTER`는 이 추천 목록의 센터만 선택할 수 있다. 목록이 비어 있으면 다른 보관 방식을 선택한다.
- P1 후보 상세에서는 사용자 인계 확정 항목에만 `사용자 인계 확인, 센터 검증 전` 문구와 센터명·연락처를 제공한다.
- 정확한 습득·보관 위치, `storageDesc`, 습득자 식별자, 원본 이미지는 어느 후보 응답에도 제공하지 않는다.

## 4. 신고, 센터 안내, 매칭

### 4.1 동적 반경과 센터 안내

신고에는 장소 핀 1개 이상을 저장한다. 서버는 신고 생성·수정 시 아래 값을 계산하고 `centerGuidance` 스냅샷과 함께 저장한다.

```text
effectiveSearchRadiusMeters = clamp(
  minRadius,
  maxRadius,
  baseRadius + coefficient × median(adjacentWaypointDistanceMeters)
)
```

초기 환경 설정값은 `minRadius=500 m`, `baseRadius=1,000 m`, `maxRadius=3,000 m`, `coefficient=0.10`이다. 정책 버전과 계산 반경을 신고에 보존한다. 신고 조회는 저장된 `centerGuidance`를 함께 반환하며, 신고 수정 때만 다시 계산한다.

### 4.2 점수와 공개 단계

```text
score = 100 × (
  0.35 × routeProximity
  + 0.20 × time
  + 0.20 × category
  + 0.15 × color
  + 0.10 × publicDescription
)
```

- 색상·공개 설명이 없으면 해당 항목은 `0`이며, 나머지 가중치를 다시 정규화하지 않는다.
- 후보는 점수 내림차순, FoundItem ID 오름차순으로 최대 5개를 저장한다.
- P0은 후보 배열 원소의 ID·순위·점수만 보인다.
- P1은 포인트 열람 뒤 제한 썸네일, 분류, 대략적 발견일, 습득자가 공개 확정한 특징을 보인다. 비센터 보관 항목의 정확한 위치·보관 설명은 계속 숨긴다.

## 5. P1 포인트와 반환

| 정책 값 | 초기값 | 비고 |
|---|---:|---|
| 가입 데모 포인트 | 10 | P1 도입 시 기존 활성 사용자에도 한 번만 부여 |
| 후보 상세 열람 비용 | 1 | `reportId + userId`당 한 번만 차감 |
| 센터 확인 반환 보상 | 5 | `CENTER_CONFIRMED` 인계와 반환 기록이 모두 있을 때만 지급 |

세 값은 모두 환경 설정으로 관리한다. 실제 결제 충전, 현물 교환, 환불은 이후 릴리스다.

## 6. 보안·보존 기준

- 포인트 결제는 소유권 검증이 아니다.
- 비공개 특징, AI 원문, 정확한 위치, 원본 이미지, 습득자 식별자는 후보·감사 로그에 넣지 않는다.
- `EXPIRED` 또는 `RETURNED`가 된 뒤 30일이 지나면 원본과 썸네일을 Object Storage에서 삭제한다. 기간은 환경 설정이다.
- 관리자 링크 토큰, JWT, 비밀번호, Object Storage 키는 응답·감사 로그에 남기지 않는다.

## 7. 수용 기준

### P0

- 사진 업로드부터 인계 확정까지의 상태 전이가 동작하며 `DRAFT` 정리와 `PENDING_HANDOVER` 후보 제외가 검증된다.
- Vision 실패와 누락 특징이 등록·매칭을 막지 않고, 수정은 후보를 stale 상태로 만든다.
- 센터 추천은 1 km 내 활성 센터 최대 10개이며, 인계 확정 시각은 서버가 기록한다.
- 신고별 센터 안내 스냅샷과 동적 반경이 재현된다.
- 후보 응답에는 ID·순위·점수 외 상세 정보가 없다.

### P1

- 기존 계정과 연결되지 않은 관리 계정이 승인·일회성 링크·활성화 흐름을 거쳐 대시보드를 사용한다.
- 담당자는 선택된 센터의 사용자 인계 주장만 실물 확인 후 수락할 수 있다.
- 신고별 후보 열람은 한 번만 차감되고, 반환 보상은 한 번만 지급된다.
- 대시보드와 React Native 담당자 화면에서 인계 수락·반환을 실제로 수행할 수 있다.
